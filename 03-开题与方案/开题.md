## 摘要

大模型已被广泛用于代码审计，但工程落地的障碍不在"检出"而在"可信"：传统静态分析（SAST）结论可复现但误报率高，开发者被迫逐条复核而逐渐弃用；大模型语义理解强、能发现逻辑类缺陷，但其结论常包含编造的漏洞与虚构的位置，**无法被验证**。两层都不可靠，导致"大模型帮你把误报过滤掉"这类方案在工程上仍不敢被相信。

本项目提出并实现一套**以动态复现为证据**的大模型代码审计系统。系统不做静态证据核对，而是把 SAST 产生的每一条候选告警送入隔离 Docker 沙箱中**实际执行**：先用 tree-sitter 提取告警所在函数及其同文件辅助函数，再由大模型生成 mock 桩拦截危险 sink、构造触发 payload，与业务源码拼装为可独立运行的单元 harness 并执行；依据 sink 入参的硬编码检测或运行日志推理判定该漏洞是否真实存在。**跑得出来才算漏洞**。

系统采用确定性外层编排程序控制全部流程与重试闭环，大模型仅输出结构化建议，不掌握流程控制权，从而保证实验可审计、可回放。判定结果分为**已确认（TP）／已排除（FP）／未确认（Unconfirmed）**三类，其中"未确认"单列统计且不计入误报，如实反映单元 harness 的方法局限。

评测采用三方对照（纯 Semgrep／纯 LLM／本系统）与六组实验，除精确率、召回率、F1、误报率外，引入**动态验证确认率**、**未确认占比**、**抑制正确率**与**第三方复现率**四项指标。其中第三方复现率由未参与该条验证的成员仅依据报告所附材料独立复现，直接检验"可验证"是否成立，构成本项目核心卖点的定量支撑。

**关键词**：代码审计；误报抑制；动态复现；Extract-Mock-Test；单元 harness；可验证性

## 一、选题背景与意义

### 1.1 社会与国家实际需求

**（1）开发者被告警淹没，工具的可信度成为瓶颈**

静态应用安全测试长期存在误报率偏高的问题。开发者需要人工逐条复核，产生两条后果：一是告警疲劳，真实漏洞被淹没在噪声中；二是开发者逐渐不信任工具输出，安全左移难以落地。**问题的本质不是检出力不足，而是结论的可信度不足。**

**（2）大模型参与审计，带来"可信"的新问题**

大模型能补上 SAST 缺乏的跨函数与业务逻辑理解能力，但它的输出是不可验证的自然语言。业界因此出现大量"用大模型过滤 SAST 误报"的方案——然而这类方案把最终判断权交给了一个本身会幻觉的模型，形成**用不可信去校正不可信**的困境。

**（3）软件供应链安全上升到国家层面**

Log4Shell 等事件后，软件供应链安全成为国家议题。《网络安全审查办法》、SBOM（软件物料清单）相关标准（SPDX / CycloneDX）相继落地，对"能否说清软件里有什么风险"提出合规要求。⚠️[待核实 A1][待核实 A2]

**（4）课程大纲明确要求安全开发内容**

教学计划第 12 次课原文要求"介绍**软件安全开发基础**，介绍代码安全的重要性"，并要求学生"学习本项目所需编程语言的**编程规范**，提升代码安全性"；评分标准亦将"**规范编程能力**"写入期末职业素养考核。**本选题与课程大纲高度一致。**

### 1.2 问题定义：代码审计的两层都不可靠

| 层次 | 代表 | 优点 | 致命缺陷 |
|---|---|---|---|
| **传统 SAST** | Semgrep、CodeQL、Bandit | 规则可控、可复现、速度快 | **误报率高**；缺跨函数上下文；业务逻辑类漏洞难以发现 |
| **纯大模型审计** | 把代码交给 LLM 找漏洞 | 语义理解强、可发现逻辑缺陷 | **幻觉严重**：编造漏洞、编造行号、结论无法复现 |

于是产生一个看似合理、实则危险的折中方案：**用大模型过滤 SAST 的误报**。这个方案的问题在于——

> 大模型说"这条告警是误报"，开发者凭什么相信？模型判断错了，真漏洞就被静默丢掉了，而且**丢失是无声的**：没有任何东西会被报错。

**根本症结在于：现有方案的结论都是"可辩解的"（arguable），而不是"可验证的"（verifiable）。** 一段自然语言推理，无论听起来多么有道理，都无法被独立复核。

### 1.3 选题意义与"可验证"的定义

**本项目把判定依据从"模型的判断"换成"代码的执行结果"。**

> **本文所称"可验证"特指：每条被采纳的漏洞结论均附带第三方可独立重复的验证材料——包括可执行的 harness 脚本、触发 payload、运行环境说明与完整运行日志，任何人据此可在自己的环境中复现同一结论。**
>
> 该含义**不同于形式化验证**（数学证明程序性质），也**不同于可验证计算**（证明外包计算结果正确），特此界定以免混淆。

意义有三：

1. **现实意义**：让自动化代码审计的结论真正可被工程采用——开发者不只能看到"这是漏洞"，还能亲手跑一遍看到它被触发。
2. **方法意义**：把"误报抑制"从模型判断问题，转化为程序可执行性与环境构建问题——后者是工程上可解决、可度量的。
3. **课程意义**：项目覆盖调研、方案设计、系统实现、实验测试、文档撰写与技术展示全流程，且与教学计划的软件安全开发内容直接呼应。

## 二、国内外研究现状

### 2.1 代码审计技术的四代演进

| 代际 | 核心技术 | 代表 | 局限 |
|---|---|---|---|
| 第一代 | 规则／模式匹配 | grep、早期 Flawfinder | 无语义，误报极高 |
| 第二代 | 数据流与污点分析 | 基于 AST + 调用图的商用 SAST | 跨函数与动态语言支持差 |
| 第三代 | 图分析 | 代码属性图（CPG）、Joern ⚠️[待核实 A3] | 需人工编写查询；语义类缺陷覆盖不足 |
| 第四代 | 神经符号（LLM + 程序分析） | IRIS ⚠️[待核实 A4]、RepoAudit 等 | 仍在演进；**报告可信度问题未被作为一等问题处理** |

### 2.2 大模型用于漏洞检测的主要路线

| 路线 | 做法 | 代表 |
|---|---|---|
| 直接提示 | 把代码片段交给 LLM 判断 | 各类零样本漏洞发现工具 |
| 检索增强 | 检索相似代码／历史修复再提示 | 基于 CVE 修复对的知识增强方法 |
| 神经符号 | LLM 生成分析规格，静态分析执行 | IRIS：LLM 生成 source/sink 规格并过滤误报路径 ⚠️[待核实 A4] |
| 多智能体 | 多角色分工协作 | RepoAudit：MetaScanAgent + DFBScanAgent ⚠️[待核实 A5] |
| 端到端 Agent | 自主检索、定位、修改代码 | AutoCodeRover、SWE-agent、OpenHands |

**本项目与上述路线的区别**：它们输出的是**判断**（这段代码是否存在漏洞），本项目输出的是**证据**（这段代码被执行并触发了漏洞）。

### 2.3 大模型用于误报过滤（本项目最直接的相关工作）

工业界已出现"用 LLM 给 SAST 告警做二次分诊"的思路，也有针对性研究，例如 *Sifting the Noise: A Comparative Study of LLM Agents in Vulnerability False Positive Filtering*（本项目参考其 Agent 只读访问仓库的实验设置）⚠️[待核实 A6]。

**这一路线的共同局限**：

- 判定仍是**自然语言推理**，结论不可独立复核；
- 模型与判定规则绑定，换模型即换结论，实验指标不稳定；
- 对"模型为何判断错误"缺少可归因的中间产物。

### 2.4 动态验证与自动化漏洞复现

**（1）DARPA AIxCC 与 Cyber Reasoning Systems**

AIxCC 推动了"自动化漏洞发现与修补"从研究原型走向工程系统，多支决赛队伍的系统已开源（如 Trail of Bits 的 Buttercup、以及 *All You Need Is A Fuzzing Brain* 系统的开源实现）⚠️[待核实 A7][待核实 A8]。这类系统普遍采用"**多组件流水线 + 可审计中间产物**"架构：

- 通过 fuzzing 触发崩溃获得**动态证据**；
- 崩溃可复现即认定漏洞存在。

**（2）与本项目的关键差异**

| | AIxCC 类 CRS | 本项目 |
|---|---|---|
| 起点 | 只有源码，无告警 | **给定 SAST 告警**（定向复现） |
| 手段 | 模糊测试寻找输入 | **Extract-Mock-Test 单元 harness** |
| 目标 | 发现尽可能多的漏洞 | **判定给定告警的真伪（误报抑制）** |
| 环境 | 完整项目构建 + 长时间 fuzzing | 局部代码 + 轻量沙箱 |

即：AIxCC 解决"**有没有漏洞**"，本项目解决"**这条告警是不是漏洞**"。后者规模小得多，但更贴近真实工程中的告警分诊场景。

### 2.5 智能体沙箱执行基础设施

本项目复用现有轻量智能体与沙箱执行层，不自研容器调度：

- **mini-swe-agent**：轻量级智能体，提供 bash 动作接口 ⚠️[待核实 A9]；
- **SWE-ReX**：面向软件工程智能体的隔离执行层，提供 Docker 沙箱 ⚠️[待核实 A10]；
- **SWE-agent / OpenHands**：同类 agent-computer interface 的代表工作。

**设计取舍**：仅将这两者用作**沙箱执行能力**，业务控制逻辑全部放在外层编排程序中，规避 LLM 自主 ReAct 带来的循环不可控与结果不稳定。

### 2.6 评测数据集

| 数据集 | 语言 | 特点 | 已知问题 |
|---|---|---|---|
| **SARD**（NIST） | 多语言，本项目取 **Python 子集** | 人工构造、每条标注所属 CWE、标签可靠 | 多为小型代码片段，真实性有限 ⚠️[待核实 A11] |
| **Defects4Py** | Python | 真实开源项目历史漏洞 commit，可得修复前后代码 | 修复 commit 不一定是安全修复，须过滤 ⚠️[待核实 A12] |
| Defects4J | Java | 同类 Java 版本 | 与"审计对象以 Python 为主"不一致，仅作跨语言可选补充 ⚠️[待核实 A13] |
| Big-Vul | C/C++ | 大规模真实 CVE | 部分样本上下文残缺，须质量过滤 ⚠️[待核实 A14] |

> **重要匹配关系**：SARD 的样本**多为单文件**，而本项目的 Extract 环节只提取**同文件内**函数——两者天然匹配。因此 SARD 被定为主评测集，用于验证流水线本身是否工作；Defects4Py 用于检验真实场景下的表现。

### 2.7 研究空白与本项目定位

**空白一：误报过滤止步于"判断"，缺少"证据"。**

现有 LLM 分诊工作把最终判断权交给模型，结论不可独立复核。"可验证性"未被作为系统设计的第一约束。

**空白二：动态验证类工作面向"发现"，而非"定向复现给定告警"。**

AIxCC 类系统从零开始 fuzzing，目标是发现漏洞；而工程现场需要的恰恰相反——**已经有 500 条告警，要判断哪条是真的**。把动态验证能力用于定向复现告警，是一条尚未被系统化的路径。

**空白三：缺少对"无法判定"这一类的诚实统计。**

现有方案只报精确率与误报率，把"验证失败"默认算作误报。这掩盖了方法局限，也无法指导后续改进。

**空白四：LLM 自主决策导致实验不可复现。**

多数 agent 方案让 LLM 自主规划流程（ReAct），重试与分支由模型决定，导致换模型即换结论、实验指标波动大。

**本项目的切入点是**：以**动态复现**作为判定证据，用**确定性外层编排**取代 LLM 自主决策，并把结果分为**已确认／已排除／未确认**三类、以**第三方复现率**度量可验证性，在公开数据集上完成三方对照与消融实验。

## 三、项目任务的主要内容和目标

### 3.1 总体目标

构建一套可运行、可复现、可演示的大模型代码审计系统，回答三个工程问题：

1. **动态复现能把误报压到什么程度**——相对纯 SAST 与纯 LLM 分诊两个基线，本系统的精确率提升多少？代价是召回率下降多少？
2. **代价是否可接受**——每条告警平均消耗多少 token、多少次 LLM 调用、多少次沙箱执行、多少人工复核时间？
3. **结论是否真的可验证**——抽样已确认漏洞中，第三方仅依据报告所附材料独立复现的成功率是多少？

### 3.2 要解决的复杂工程问题

> 给定 SAST 产生的高噪声告警集合，构建一条能**自动完成"提取—建模—执行—判定"闭环**的流水线，使每条被采纳的漏洞结论都附带**第三方可独立复现**的运行证据；同时如实刻画"无法判定"的比例，而非将其掩盖为误报。

该问题的复杂性在于：它同时涉及多语言程序分析（AST 切片）、大模型代码生成（mock 与 payload）、容器沙箱调度、依赖环境重建、确定性状态机编排与评测方法论，且核心矛盾（**召回率 vs 可信度**）无法通过单一技术手段解决。

### 3.3 具体建设内容

| 编号 | 建设内容 | 说明 |
|---|---|---|
| C1 | **SAST 扫描与告警预处理** | Semgrep 规则扫描 + tree-sitter 定位告警所属函数节点 + 告警去重 |
| C2 | **LLM 静态理解模块** | 以告警、局部源码与 CWE 为输入，输出结构化漏洞信息（source／transformations／sink／CWE） |
| C3 | **Extract 代码提取工具** | 基于 tree-sitter 提取 sink 函数及同文件辅助函数，封装为独立可执行程序 |
| C4 | **Mock 生成与 harness 组装** | 大模型生成 mock 桩与 payload，拼装为可独立运行的单元测试脚本 |
| C5 | **沙箱执行与判定** | SWE-ReX 隔离 Docker 沙箱执行 harness；硬编码检测器或日志推理判定 |
| C6 | **确定性编排与重试闭环** | 外层程序控制全部流程、重试计数与分支判决，LLM 仅出建议 |
| C7 | **报告汇总与评测** | 三分类结果、8 项指标、E1–E6 实验、可视化审计报告 |

### 3.4 预期成果

1. 可运行的代码审计系统一套（输入项目 → 输出带可复现证据的审计报告）
2. Extract-Mock-Test 动态验证流水线一套（本项目核心贡献）
3. 实验数据与图表：三方对照 + 六组实验 + 8 项指标的实测值
4. 中期报告与课程总结报告各一份，参考文献不少于 8 项并符合 GB/T 7714—2015 规范
5. 技术展示 PPT 一份

## 四、方案设计与技术路线

### 4.1 总体架构

```
┌──────────────┐   ┌──────────────┐   ┌────────────────────────────┐
│ SAST 扫描     │──▶│ 告警预处理    │──▶│ LLM 静态理解                │
│ Semgrep      │   │ tree-sitter  │   │ DeepSeek API                │
│ (C1)         │   │ 定位函数节点  │   │ → source/transformations/   │
└──────────────┘   └──────────────┘   │   sink/CWE 结构化输出 (C2)   │
                                       └─────────────┬──────────────┘
                                                     │ 候选漏洞
                        ┌────────────────────────────▼──────────────────────┐
                        │        动态验证：Extract-Mock-Test (C3–C5)          │
                        │  ① Extract：tree-sitter 提取 sink 函数+同文件辅助   │
                        │  ② Mock：LLM 生成 mock 桩 + 触发 payload，组装 harness│
                        │  ③ Test：SWE-ReX Docker 沙箱执行，捕获完整日志       │
                        │  ④ 判定：硬编码检测器 / 日志推理 → TP/FP/未确认      │
                        └────────────────────────────┬──────────────────────┘
                                                     │
                        ┌────────────────────────────▼──────────────────────┐
                        │   确定性外层编排程序 (C6)                          │
                        │   重试计数器 · 分支判决 · 预算控制 · 全程落盘        │
                        └────────────────────────────┬──────────────────────┘
                                                     │
                        ┌────────────────────────────▼──────────────────────┐
                        │   报告汇总与评测 (C7)                              │
                        │   三分类结果 · 8 项指标 · E1–E6 · 可视化报告         │
                        └───────────────────────────────────────────────────┘
```

**核心设计原则**：

1. **判定依据必须是执行结果，不是模型表述**；
2. **流程控制权必须在确定性代码手里，不在 LLM 手里**；
3. **无法判定的必须单列，不能并入误报**。

### 4.2 模块一：SAST 扫描与告警预处理（C1）

| 组件 | 作用 | 说明 |
|---|---|---|
| **Semgrep** | 规则扫描，输出原始告警 | 采用官方规则集**默认配置**，不针对评测基准手工调优，保证基线公平 ⚠️[待核实 A15] |
| **tree-sitter** | 定位告警所在行所属的语法函数节点 | 为 LLM 提供局部上下文；同时用于告警去重 |

告警原始信息包括：位置、CWE 类型、sink／source 标记、规则标识、污点路径（若规则提供）。

> 若规则覆盖不足，可切换或并用 CodeQL ⚠️[待核实 A16]，切换时须记录版本与规则集，保证可比性。

### 4.3 模块二：LLM 静态理解（C2）

**输入配置（方案 A 为默认，方案 B 为对照）**：

- **方案 A**：SAST 原始告警 + 告警对应局部源码片段（tree-sitter 定位）+ 对应 CWE 类型；
- **方案 B**：仅给告警 + 仓库**只读**访问权限，由 agent 通过 bash 自主读取源码（参考 *Sifting the Noise* 的实验设置）⚠️[待核实 A6]。

**输出结构化 JSON**：

```json
{
  "source": {"type": "...", "name": "...", "line": 0},
  "transformations": [{"function": "...", "line": 0, "sanitized": false}],
  "sink": {"function": "...", "file": "...", "line": 0, "dangerous": true},
  "vulnerability_type": "...",
  "cwe_id": "CWE-XXX",
  "confidence": 0.0
}
```

**重要约束**：

- 该阶段输出**一律进入下游动态验证，任何情况下不直接采纳**；
- `confidence` 字段**仅作记录，不参与最终判定**——本项目的立场是"模型自报的把握不能作为控制量"。

### 4.4 模块三：动态验证——Extract-Mock-Test（C3–C5，核心）

#### 4.4.1 Extract：局部代码提取（C3）

自研 tree-sitter 脚本，封装为独立可执行程序。输入目标文件路径与 sink 函数位置，输出 sink 函数及**同文件内**被直接调用的辅助函数源码片段。

**已知局限**：不跨文件，故会丢失跨文件的 source 与净化逻辑。缓解手段有三：

1. 优先选用**单文件可复现**的样本（SARD 天然满足）；
2. 对跨文件样本，可向上追有限深度的调用链（可选扩展）；
3. 无法复现者归入"**未确认**"，如实统计，不冒充误报。

#### 4.4.2 Mock：桩生成与 harness 组装（C4）

调用 DeepSeek API，传入提取源码、sink／source 信息与 CWE 类型，生成 mock 补丁与触发 payload，将业务源码与 mock 桩拼装为独立可执行的单元测试脚本。

**mock 的作用**：拦截危险 sink 调用、捕获函数入参、返回模拟返回值，**避免真实执行高危系统调用**（这一点同时也是合规要求，见 6.5）。

**这是全系统失败率最高的环节**，因此设计上采取两项措施：

- **模板化 + few-shot**：不采用全自由生成，而是给定输出模板与 2–3 个示例，LLM 只填参数，显著降低语法错误与依赖缺失；
- **失败率统计**：mock 组装失败率作为独立观测项，不隐藏。

#### 4.4.3 Test：沙箱执行（C5）

**先准备依赖环境**：为每个被测项目维护依赖清单（`requirements.txt`）或预构建镜像，沙箱内先完成依赖安装；安装失败记为**环境问题**，不计入模型效果评估。

**再执行 harness**：借助 mini-swe-agent 的 SWE-ReX 隔离 Docker 沙箱部署 harness，送入 payload 执行，捕获 stdout／stderr 完整日志。

#### 4.4.4 判定

两种模式**由 E2 实验比选**（不作为悬置项）：

| | 模式 A 硬编码检测器 | 模式 B LLM 日志推理 |
|---|---|---|
| 机制 | 检测器嵌入 harness，由 mock 捕获 sink 入参并输出结构化结果 | 固定提示词模板，输入源码／mock／payload／日志／报错／告警／CWE，输出结构化 JSON |
| 优点 | 确定性强、无 LLM 幻觉 | 覆盖面宽 |
| 局限 | 更适配注入类漏洞 | 又引入一层模型判断，与方法论立场有张力 |
| 输出 | `{verdict, reason}` | `{verdict, reason, fix_suggestion}` |

模式 B 的提示词模板**必须区分**两类失败原因：①mock／harness 环境错误；②payload 未能触发。**后者不等同于漏洞不存在**，只是本次构造不成功。

### 4.5 模块四：确定性编排与重试闭环（C6）

外层编排程序维护重试计数器（默认上限 3 次，可配置），按判定结果执行分支：

| 条件 | 动作 |
|---|---|
| `verdict = TP` | 保存 finding（harness、payload、日志），结束 |
| `verdict = FP` 且建议改 mock | 调用 LLM 修改 mock → 重新组装 harness → 重跑 |
| `verdict = FP` 且建议改 payload | **仅更新 payload**，复用现有 harness 重跑（省一次 mock 生成） |
| 达到重试上限 | 标记「**未确认**」，**不计入误报统计**，占比单独报告 |

**预算控制**：为单条告警设置 LLM 调用次数与沙箱执行次数上限，超出即转"未确认"，避免成本失控。

**设计要点**：**LLM 只输出结构化建议，不决定分支走向**。这一约束使实验流程可审计、可回放，指标稳定。

### 4.6 接口契约（第一周冻结，避免并行开发互相阻塞）

```python
def audit_alert(alert: dict, config: dict) -> AlertResult:
    """
    返回 AlertResult：
      alert_id, cwe, config_id,
      static_understanding: {source, transformations, sink, cwe_id, confidence},
      extract:   {snippet_path, functions: [...], cross_file_missing: bool},
      harness:   {script_path, mock_patch, payload, assemble_ok: bool, assemble_error},
      run:       {exit_code, stdout, stderr, elapsed_s, env_ok: bool},
      verdict:   {label: "TP"|"FP"|"Unconfirmed", reason, mode: "A"|"B"},
      retries:   [{round, branch, change, result}],
      evidence:  {harness_sha, payload_sha, env_snapshot, replay_command},
      overhead:  {llm_calls, prompt_tokens, completion_tokens, sandbox_runs}
    """
```

三人只通过 `audit_alert` 与 `AlertResult` 交互，**契约冻结后可完全并行开发**。

### 4.7 评测数据集

| 数据集 | 定位 | 抽样规模 |
|---|---|---|
| **SARD**（Python 子集） | 受控主评测集，验证流水线是否工作 | ⚠️ 待定，建议 30–50 个样本 |
| **Defects4Py** | 真实漏洞集，检验真实场景表现 | ⚠️ 待定，建议 30–50 条告警 |
| Defects4J / Big-Vul | 跨语言泛化可选补充 | 时间不足时不纳入 |

**抽样与标注**：固定随机种子自动抽样；以数据集标注为一阶真值，对采纳集与已排除告警按固定比例人工抽样复核，作为二阶真值。

**合规**：全部为公开数据集，不使用爬虫、不使用真实业务代码与真实个人信息。

### 4.8 评测指标与实验设计

#### 指标（8 项）

| 指标 | 定义 |
|---|---|
| 精确率、召回率、F1 | 采纳集相对数据集真值标注的准确与覆盖程度 |
| 误报率 | 采纳集中实际为误报的结论占比 |
| **动态验证确认率** | 已确认（TP）告警占进入动态验证告警的比例 |
| **未确认占比** | 未确认（Unconfirmed）告警占全部候选告警的比例，**单独报告，不并入误报** |
| **抑制正确率** | 已排除（FP）告警中经人工抽样确认为误报的比例 |
| **第三方复现率** | 抽样已确认漏洞中，由**未参与该条验证的成员**仅依据报告所附材料独立复现成功的比例 |
| 人工复核成本 | 每条结论的平均人工复核耗时（抽样实测） |
| 开销 | token 消耗、LLM 调用次数、沙箱执行次数、端到端时延 |

> **第三方复现率是本项目的核心指标**：它直接检验"可验证"是否成立，也是本方案区别于"LLM 分诊"方案的最有力证据。

#### 实验设计

| 实验 | 自变量 | 观测 |
|---|---|---|
| **E1 三方对照** | 纯 Semgrep（告警全采纳）／纯 LLM（静态理解后直接采纳）／本系统（完整动态验证） | 精确率、召回率、F1、误报率、动态验证确认率、未确认占比 |
| **E2 消融与模式比选** | 无动态验证／仅模式 A／仅模式 B／完整重试闭环 | 各组件边际贡献；**完成判定模式比选** |
| **E3 跨基准泛化** | SARD（合成）／Defects4Py（真实） | 结论是否一致 |
| **E4 跨模型泛化** | 两个大模型 | 结论是否与模型绑定 |
| **E5 成本与收益** | 验证配置 | token、LLM 调用、沙箱次数、时延 vs 可信度提升 |
| **E6 典型案例溯源** | — | 成功与失败样本逐条分析 |

**核心图**：「**可信度—召回率**」权衡曲线（动态验证提升精确率 vs 单元 harness 复现局限导致召回损失），以及 E2 消融柱状图。

5. **合规声明见 6.5**。

### 6.5 合规声明（对动态执行的特别说明）

> 本项目为课程教学与防御性研究用途。动态验证在**隔离 Docker 沙箱**中进行，且 mock 桩会**拦截危险 sink 调用**（如数据库执行、系统命令、文件写入），使其**不产生真实副作用**；所有 payload 均为合成构造的测试输入，不含真实攻击载荷。项目**不针对任何未授权的第三方系统**，所产出的 harness 与 payload **仅用于验证告警真伪**，不得用于攻击活动。

## 七、风险分析与应对

| 编号 | 风险 | 影响 | 应对 |
|---|---|---|---|
| **R1** | **Mock 生成失败率高**（语法错、缺依赖、拦截逻辑不对） | 流水线大量卡在组装环节 | 模板化 + few-shot；把组装失败率作为独立观测项；设重试上限 |
| **R2** | **Docker／SWE-ReX 在本机不稳定** | 沙箱执行不可用，项目停滞 | 已实测本机有 Docker 29.5.3 + WSL2 Ubuntu-24.04；**开工第一件事启动 daemon 并验证**；降级方案：改用直接 `docker run` 驱动 |
| **R3** | **跨文件样本无法 Extract** | 复现失败，召回损失 | 优先单文件样本（SARD）；跨文件样本归入"未确认"并如实统计 |
| **R4** | **被测项目依赖装不上** | harness 跑不起来 | 维护依赖清单／预构建镜像；安装失败记为环境问题，不计入模型效果 |
| **R5** | **重试烧 token** | 成本失控 | 单告警 LLM 调用与沙箱次数上限；超限转"未确认" |
| **R6** | 未确认占比过高 | 采纳集过小 | 这是**方法的真实局限**，如实报告；通过收窄 CWE 范围（聚焦注入类）改善 |
| **R7** | 判定模式 B 引入 LLM 再判断 | 与方法论立场冲突 | 由 E2 比选；若模式 A 足够，以 A 为准，B 仅作对照 |
| **R8** | 引用了未核实的项目／论文 | 学术规范问题 | 全文 ⚠️[待核实] 标记 + 附录 A 清单 + 定稿前逐项核实 |
| **R9** | 三人并行出现接口漂移 | 集成返工 | 第一周冻结 `audit_alert` 契约；每阶段末联调 |

**降级预案**（按保留优先级）：

1. **保留**：SAST 扫描 + Extract + Mock + 沙箱执行 + 判定（主链路必须跑通）
2. **可砍**：模式 B（LLM 判定）、方案 B（agent 自读代码）、Defects4J／Big-Vul 跨语言
3. **可缩**：样本规模缩至 20 条；CWE 范围缩至 CWE-89／78／22 三类
4. **最后手段**：把"未确认"比例如实报告，以"方法论局限的实证研究"定位交付

## 八、创新点与预期难点

### 8.1 创新点

1. **判定依据从"模型判断"改为"执行证据"**：把误报抑制问题转化为"给定告警能否在隔离环境中被定向复现"的工程问题，使每条采纳结论都附带第三方可独立重复的材料（harness、payload、环境、日志、复现命令）。

2. **以确定性外层编排取代 LLM 自主决策**：LLM 只输出结构化建议，重试与分支由确定性代码控制。这使得流程可审计、可回放，实验指标不受模型自主性波动影响——这是相对同类 agent 方案的实质改进。

3. **三分类 + 未确认单列**：把"验证失败"与"确实是误报"严格区分，未确认不计入误报统计。这一处理如实刻画了方法局限，避免了该领域常见的指标美化。

4. **引入第三方复现率作为可验证性的量化指标**：由未参与该条验证的成员独立复现，把"可验证"从一个形容词变成可测的数字。

5. **针对性复用现有基础设施**：复用 SWE-ReX 隔离沙箱，把工程工作量集中在 Extract-Mock-Test 这一真正有难度的环节，而非重复开发容器调度。

### 8.2 预期难点

| 难点 | 说明 | 应对 |
|---|---|---|
| **mock 的可靠性** | LLM 生成的 mock 常有语法与拦截逻辑错误，是全系统最大瓶颈 | 模板 + few-shot；失败率公开统计；重试上限 |
| **跨文件上下文缺失** | Extract 只取同文件，丢失跨文件 source 与净化逻辑 | 优先单文件样本；跨文件归入"未确认"并讨论 |
| **依赖环境重建** | 被测项目的运行时依赖不确定 | 依赖清单／预构建镜像；环境问题与模型效果分开统计 |
| **判定归因** | 跑不出来时，区分"环境错"与"payload 错"很难 | 模式 A 为主；模式 B 仅辅助；必要时人工抽样复核 |
| **CWE 覆盖面** | Extract-Mock-Test 主要适配注入类漏洞 | **明确把范围限定为注入类**（CWE-89／78／22 等），报告中写明 |
| **召回损失** | 严格验证必然削掉部分真漏洞 | 用"可信度—召回率"曲线如实呈现，不只看精确率 |
