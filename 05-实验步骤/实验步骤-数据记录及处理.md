## 3.1 实验总体流程

本项目按"环境与数据准备 → SAST 扫描与告警预处理 → LLM 静态理解 → 动态验证（Extract-Mock-Test）→ 判定与重试 → 报告汇总 → 评测分析"七个阶段推进，前六个阶段由系统自动完成，各阶段均产出结构化记录文件，以保证实验过程可追溯、结果可复现。

## 3.2 实施步骤

S1 环境搭建与版本固定。Python 3.12、Docker（隔离沙箱）、mini-swe-agent（复用其内置 SWE-ReX 隔离 Docker 沙箱）、tree-sitter（Python 绑定）、Semgrep（`pip install` 安装，官方规则集默认配置；如规则覆盖不足切换或并用 CodeQL，切换时记录版本与规则集）；配置 DeepSeek API 与调用限额；全部组件固定版本。产出 `env.json`。

S2 数据集准备与抽样。**审计对象语言以 Python 为主。** 受控主评测集用 SARD 的 Python 子集（人工构造，每条样本标注所属 CWE，据此判定 SAST 告警真伪，标签可靠）；真实漏洞集用 **Vul4Py**（Python，约 60 类 CWE、每个漏洞带测试套件），以漏洞版本代码的 SAST 原始告警对照修复 commit 构造 ground-truth（**注：原任务书写作 Defects4Py，经 A12 考证确认其为一般性缺陷集而非安全漏洞集，已更正为 Vul4Py，考证记录见 `数据集选型决策(Defects4Py考证A12).md`**）；Defects4J（Java）与 Big-Vul（大规模真实 CVE，须先过滤上下文残缺样本）仅作为跨语言泛化验证的可选补充，时间不足时不纳入主流程；以固定随机种子自动抽样，避免人工挑选引入偏差。产出 `dataset_manifest.json`。

S3 SAST 规则扫描。用 Semgrep 以官方规则集默认配置扫描全部目标项目，不针对评测基准手工调优，保证其作为基线对照时的公平性。产出 `sast_alerts.json`（告警位置、CWE 类型、sink/source 标记、污点路径等原始信息，作为整个系统的输入）。

S4 告警预处理与上下文定位。用 tree-sitter 解析目标项目，定位每条告警所在行所属的语法函数节点；对告警去重。产出 `alert_context.jsonl`。

S5 LLM 静态理解。调用 DeepSeek API 完成静态代码理解，默认输入为 SAST 原始告警、告警局部源码片段（tree-sitter 定位）与对应 CWE 类型（方案 A）；"Agent 工具访问"输入（方案 B，mini-swe-agent 经 bash 只读访问仓库自主读取源码）作为对照配置。输出机器可读 JSON 结构化漏洞信息（source、transformations 及净化标记、sink、vulnerability_type、cwe_id、confidence）。该阶段仅为静态推理、存在幻觉风险，其输出一律进入下游动态验证，不直接采纳。产出 `static_findings.jsonl`。

S6 Extract 函数提取。自研 tree-sitter 脚本封装为独立可执行程序，输入目标文件路径与 sink 函数位置，输出 sink 函数及同文件内被直接调用的辅助函数源码片段。产出 `extracted_snippets/`。

S7 Mock 桩生成与 harness 组装。调用 DeepSeek API，传入提取源码、sink/source 信息与 CWE 类型，生成 mock 补丁与触发 payload；将业务源码片段与 mock 桩拼装为独立可执行的 harness 单元测试脚本。mock 负责拦截危险 sink 调用、捕获函数入参并返回模拟返回值，避免真实执行高危操作。产出 `harness/`（harness 脚本、mock 补丁、payload）。

S8 沙箱执行。**先为被测项目准备依赖环境**：为每个目标项目维护依赖清单（`requirements.txt`）或预构建镜像，沙箱内先完成依赖安装；依赖安装失败记为环境问题、不计入模型效果评估。随后借助 mini-swe-agent 内置 SWE-ReX 隔离 Docker 沙箱部署 harness，送入 payload 执行，捕获 stdout/stderr 完整运行日志。产出 `run_logs/` 与 `env_snapshot.json`。

S9 漏洞判定。两种模式待实验比选：模式 A 为嵌入 harness 的硬编码检测器，由 mock 捕获 sink 入参并输出结构化检测结果，确定性强、无 LLM 幻觉，适配注入类漏洞；模式 B 为 LLM 日志推理判定，判定规则由我方设计，以固定提示词模板输入源码、mock 定义、payload、运行日志、报错信息、原始告警与 CWE 类型，区分"mock／harness 环境错误"与"payload 未能触发"两类失败原因（**后者不等同于漏洞不存在**，须结合重试与人工抽样复核判定），强制输出结构化 JSON（verdict：TP/FP/未确认、reason、fix_suggestion）。产出 `verdicts.jsonl`。

S10 重试闭环。外层编排程序维护重试计数器并设置最大重试上限（建议 3 次，可配置）：verdict=TP 保存 finding（harness、payload、运行日志）并结束；verdict=FP 且 fix_suggestion 为 mock 错误，调用 DeepSeek 修改 mock 后重新组装并重跑；verdict=FP 且 fix_suggestion 为 payload 未能触发，仅更新 payload、复用现有 harness 重跑；**达到最大重试次数仍未得出确定结论的，标记为「未确认」，不计入误报统计，单独统计其占比**。payload 未能触发场景不重新生成 mock，以减少 LLM 调用开销。产出 `retry_trace.jsonl`。

S11 报告汇总输出。外层编排程序汇总每条告警的全链路处理结果（LLM 静态理解输出、动态验证 verdict、harness 与 payload 证据、运行日志），去重并按 CWE 类型与风险严重程度分级；区分"动态验证确认漏洞（附可复现 harness 证据）"与"静态候选告警（未通过动态验证）"两类；输出 JSON/Markdown 审计报告，含项目统计摘要与逐条 finding 详情。产出 `audit_report.json` 与 `audit_report.md`。

S12 评测分析。以数据集标注为真值计算指标，完成 E1–E6 实验与图表生成。产出 `metrics/` 目录。

其中 S6 至 S8 的中间产物分别落盘于 `extracted_snippets/`、`harness/`、`run_logs/`，判定与重试结果统一写入 `verdicts.jsonl` 与 `retry_trace.jsonl`。

## 3.3 判定规则

判定结果分为**三类**，只有前两类进入采纳与否决的统计：

（1）**已确认（TP）**：verdict=TP 的告警予以采纳，标记"动态验证确认"，并附带可复现证据（harness 脚本、payload、依赖与镜像版本、运行命令、完整运行日志），使第三方可独立重复该结论。

（2）**已排除（FP）**：payload 已触发目标 sink 且运行日志表明不构成漏洞，或经人工抽样复核确认为误报的告警，予以否决，不进入采纳集，**计入误报抑制统计**。

（3）**未确认（Unconfirmed）**：因依赖安装或沙箱等环境问题未能完成验证，或达到最大重试次数仍未得出确定结论的告警，不进入采纳集，**不计入误报抑制统计**，其占比单独报告。该类告警多为单元 harness 难以复现（如依赖跨文件全局状态或净化逻辑）的样本，是方法局限的直接体现。

（4）LLM 静态理解阶段的输出在任何情况下均不直接采纳，必须经过动态验证。

## 3.4 实验设计与对照

E1 三方对照。自变量为工具配置（纯 Semgrep：原始告警全部采纳／纯 LLM：SAST 告警 + LLM 静态理解、不做动态验证／本系统：完整动态验证），观测精确率、召回率、F1、误报率、动态验证确认率与未确认占比。

E2 消融实验。自变量为验证配置（无动态验证／仅模式 A 硬编码检测／仅模式 B LLM 日志推理／完整重试闭环），观测各组成部分的边际贡献，并完成判定模式比选。

E3 跨基准泛化。自变量为评测基准（SARD 的 Python 子集：合成标注／Vul4Py：真实漏洞；若时间允许再补 Defects4J、Big-Vul 作跨语言扩展），观测结论在两类基准上是否一致。

E4 跨模型泛化。自变量为大模型（2 个），观测结论是否与特定模型绑定。

E5 成本与收益。自变量为验证配置，观测 token 消耗、LLM 调用次数、沙箱执行次数、端到端时延与可信度提升之间的权衡。

E6 典型案例溯源。观测成功与失败样本的逐条过程分析。

其中 E1 确立基线，E2 支撑核心论点并完成判定模式比选，E3、E4 检验结论普适性，E5 回答工程可行性，E6 服务技术展示与归因分析。

## 3.5 数据处理与指标计算

| 指标 | 定义与计算方式 |
|---|---|
| 精确率、召回率、F1 | 采纳集相对于数据集真值标注的准确程度与覆盖程度 |
| 误报率 | 采纳集中实际为误报的结论占比 |
| 动态验证确认率 | 已确认（TP）告警占进入动态验证告警的比例 |
| **未确认占比** | 未确认（Unconfirmed）告警占全部候选告警的比例，单独报告，用于呈现单元 harness 的方法局限 |
| 抑制正确率 | 已排除（FP）告警中经人工抽样标注确认为误报的比例 |
| **第三方复现率** | 抽样已确认漏洞中，由未参与该条验证的成员依据报告所附可复现材料独立复现成功的比例 |
| 人工复核成本 | 每条结论的平均人工复核耗时（抽样实测） |
| 开销 | token 消耗、LLM 调用次数、沙箱执行次数与端到端时延 |

数据流向为：原始告警 → 静态理解输出 → 动态验证判定 → 采纳集 → 聚合指标 → 图表；派生数据一律由脚本从原始记录自动生成，不手工填写。其中精确率与误报率依赖人工标注，采用固定比例随机抽样、两名成员独立判定、分歧提交第三人仲裁的方式，并记录标注一致性。

**第三方复现率**采用交叉验证方式测定：由未参与该条漏洞验证的成员，仅依据报告中附带的可复现材料（harness 脚本、payload、依赖与镜像版本、运行命令、运行日志）独立操作一遍，记录是否得到同一结论。该指标直接检验"可验证"是否成立，是核心卖点的定量支撑。

结果呈现：E1 三方对照主表、"可信度—召回率"权衡曲线（量化动态验证提升精确率与单元 harness 复现局限导致召回损失之间的定量关系）、E2 消融柱状图、失败样例归因分析表。

## 3.6 数据记录规范与质量控制

全部记录统一存放于 `records` 目录，文件与 3.2 节各步骤的产出项一一对应，并遵循以下原则：

（1）**只追加不修改、可定位**：原始记录不得事后编辑，任何修正均以新增记录的形式体现；每条记录携带运行编号、时间戳、模型标识、配置哈希与随机种子，保证任一结论均可追溯到具体的一次运行；

（2）**版本与参数固定、结果缓存**：开源组件与 mini-swe-agent 固定到具体版本或 commit 并记录于 `env.json`；大模型温度、提示词模板与随机种子全程一致；相同输入与配置的运行结果落盘复用，避免结果漂移与配额浪费；

（3）**结果真实**：SAST 扫描失败、harness 无法组装、沙箱执行失败与复现失败的样本均如实保留，并在报告中作为方法局限（如 Extract-Mock-Test 丢失跨文件全局状态与净化逻辑导致的复现失败）加以讨论；指标、图表与截图均由脚本从原始记录生成，来自系统实际运行输出，不篡改、不伪造。
