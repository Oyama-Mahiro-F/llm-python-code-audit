# 实验步骤、数据记录及处理（详版·备期末报告用）

> 依据《项目方案》（可验证的大模型代码审计系统，简化流水线架构）编写。与早期"四级静态证据验证"方案相比，本流程将验证重心从"静态证据核对"转移到"沙箱动态复现"：不再构建 Joern 代码属性图、不设 V1–V3 前置校验，改为以 Extract-Mock-Test 单元 harness 在隔离沙箱中实际执行告警对应代码，用可复现的运行证据判定漏洞真伪。该取舍消除了程序图内存压力，代价是 SAST 证据缺陷类告警全部流入下游，增加 LLM 调用与沙箱资源开销——这一代价作为 E5 的观测对象。

## 3.1 实验总体流程

本项目按"环境与数据准备 → SAST 扫描与告警预处理 → LLM 静态理解 → 动态验证（Extract-Mock-Test）→ 判定与重试 → 报告汇总输出 → 评测与数据处理"七个阶段顺序推进。其中前六个阶段由系统自动完成，第七阶段为实验分析。各阶段均产出结构化数据记录文件，以保证实验过程可追溯、结果可复现。

整体调度方式：外层编排程序作为总控制器，以确定性代码实现全部业务控制逻辑（扫描调度、提取、组装、执行、判定分支与重试）；mini-swe-agent 负责沙箱执行能力；自研工具（Extract 等）封装为独立可执行脚本经 bash 调用，不作为 Agent 原生工具，规避 LLM 自主 ReAct 带来的循环不可控问题。

## 3.2 实验环境与工具链准备

### 步骤 S1：环境搭建与版本固定

（1）开发环境采用普通 CPU 计算机，无需 GPU，全部模型推理通过 DeepSeek 云端 API 调用完成；本地 CPU 负责编排、脚本处理与沙箱调度。操作系统为 Windows 11（或 Linux），编程语言 Python 3.12。

（2）安装 Docker，用于构建动态验证所需的隔离沙箱环境。

（3）部署 mini-swe-agent，复用其内置 SWE-ReX 隔离 Docker 沙箱执行能力；mini-swe-agent 仅提供 bash 动作接口。

（4）安装 tree-sitter 及所需语言语法包（Java、Python、C/C++ 等），用于 AST 解析与函数定位。

（5）安装 Semgrep（`pip install` 安装，不接触源码），采用其官方规则集默认配置，保证其作为基线对照时的公平性，不针对评测基准手工调优；如规则覆盖不足，切换或并用 CodeQL，并在 env.json 中记录相应版本与规则集。

（6）配置 DeepSeek API，记录模型标识与版本，设置调用限额与并发上限。

数据记录：生成 env.json，逐项记录各组件名称、版本号或 commit、安装来源、许可证类型；同时记录 API 的模型标识、温度参数与调用限额。

## 3.3 数据集准备与抽样

### 步骤 S2：评测数据集准备

（1）以 SARD（Software Assurance Reference Dataset）的 **Python 子集**作为受控主评测集：NIST 维护、工业界常用安全基准，人工构造的可控测试用例，每条样本标注所属 CWE，据此判定 SAST 每条告警的真伪，ground-truth 可靠，适合受控实验；局限为多为小型代码片段，不是真实开源项目，与真实业务代码存在差距。**审计对象语言以 Python 为主**，其他语言样本不纳入主流程。

（2）以 **Vul4Py（Python）**作为真实漏洞集：100 个真实漏洞、约 60 个开源 Python 项目、覆盖约 60 类 CWE，**每个漏洞带测试套件**，可获取漏洞修复前后代码。ground-truth 构造方式：对漏洞版本代码运行 SAST（Semgrep/CodeQL）采集原始告警，再对照修复 commit / 测试套件标注每条告警的真伪；注意修复 commit 不一定是安全修复，须过滤只保留安全类改动。**（注：数据集名称已更正——原任务书写 Defects4Py，A12 考证确认该名字在文献中多指一般性缺陷集而非安全漏洞集，与"污点流漏洞真值"需求不匹配；已更正为 Vul4Py，BugsInPy 列为可选对照，考证记录见 `数据集选型决策(Defects4Py考证A12).md`。）**

（3）Defects4J（Java）与 Big-Vul（大规模真实 CVE）作为**跨语言泛化验证的可选补充**，时间不足时不纳入主流程；Big-Vul 部分样本上下文残缺，须先按质量规则过滤。

抽样原则：采用固定随机种子进行抽样，抽样过程由脚本自动完成并输出清单，避免人工挑选引入选择偏差。

数据记录：生成 dataset_manifest.json，逐条记录项目名称、编程语言、代码规模（文件数与代码行数）、所含 CWE 类型、数据来源与许可证、ground-truth 标注方式，以及过滤规则与过滤前后样本数。

## 3.4 SAST 扫描与告警预处理

### 步骤 S3：SAST 规则扫描

使用 Semgrep 以官方规则集默认配置扫描全部目标项目，输出原始告警集合：告警位置、CWE 漏洞类型、sink/source 标记与污点路径等原始信息，作为整个系统的输入。

数据记录：输出 sast_alerts.json，记录规则标识、命中位置、CWE 标签与元变量绑定值；同时记录规则集版本、扫描总耗时，以及按 CWE 分类的命中数量统计。

### 步骤 S4：告警预处理与上下文定位

使用 tree-sitter 解析目标项目，定位每条告警所在行所属的语法函数节点，为 LLM 静态理解提供局部源码上下文；同时对告警去重（同文件、同行、同规则的告警合并）。

数据记录：输出 alert_context.jsonl，记录告警编号、文件路径、告警行、所属函数节点范围（起止行）与去重统计。

## 3.5 LLM 静态理解

### 步骤 S5：静态推理与结构化输出

调用 DeepSeek API 对每条告警完成静态代码理解，输出机器可读 JSON 结构化漏洞信息，作为下游动态验证模块的输入。

输入配置（两种，默认方案 A，方案 B 作为对照配置）：

- **方案 A**：SAST 原始告警 + 告警对应局部源码片段（tree-sitter 定位告警行所属的语法函数节点）+ 对应 CWE 漏洞类型；
- **方案 B**：SAST 告警 + Agent 工具访问权限。参考论文 *Sifting the Noise: A Comparative Study of LLM Agents in Vulnerability False Positive Filtering* 的实验设置，仓库只读访问，由 mini-swe-agent 依据推理需求通过 bash 工具自主完成源码读取。

输出结构：

```json
{
  "source": {"type": "...", "name": "...", "line": 0},
  "transformations": [{"function": "...", "line": 0, "sanitized": false}],
  "sink": {"function": "...", "file": "...", "line": 0, "dangerous": true},
  "vulnerability_type": "...",
  "cwe_id": "CWE-XXX",
  "confidence": 0.0
}
```

⚠️ **该阶段仅为 LLM 静态推理，存在幻觉风险**，输出的 source、sink、污点链路可能虚构，因此其输出一律进入下游动态验证，在任何情况下不直接采纳。提示词模板与温度参数全程固定并完整记录。

数据记录：输出 static_findings.jsonl；同时统计单条生成耗时、token 消耗与 JSON 解析失败率。

## 3.6 动态验证：Extract-Mock-Test 单元 harness

主流水线采用 Extract-Mock-Test 单元 harness 验证方案；完整项目部署测试作为可选扩展，不纳入主流程。

### 步骤 S6：Extract 函数提取

自研 Extract 工具基于 tree-sitter 做 AST 解析，封装为独立可执行脚本，由外层编排程序驱动 mini-swe-agent 通过 bash 调用。输入为目标文件路径与 sink 函数位置；输出为 sink 函数及同文件内被直接调用的辅助函数源码片段。

已知局限：仅提取局部代码，丢失跨文件全局状态与跨文件净化逻辑，部分真实漏洞可能无法在单元脚手架内复现——此类失败样本如实记录，纳入 E6 归因分析。

数据记录：输出 extracted_snippets/ 目录，每条告警一个子目录，记录提取范围、包含函数清单与提取失败原因。

### 步骤 S7：Mock 桩生成与 harness 组装

外层编排程序调用 DeepSeek API，传入提取源码、sink/source 信息与 CWE 类型，生成 mock 补丁代码；将业务源码片段与 mock 桩拼装为独立可执行的 harness 单元测试脚本。mock 负责拦截危险 sink 调用、捕获函数入参并返回模拟返回值，避免真实执行高危系统调用；同时生成用于触发漏洞的 payload。

数据记录：输出 harness/ 目录，逐告警保存 harness 脚本、mock 补丁、payload 与组装日志；记录组装失败（语法错误、依赖缺失等）的告警清单。

### 步骤 S8：沙箱执行

**先为被测项目准备依赖环境**：为每个目标项目维护依赖清单（`requirements.txt`）或预构建镜像，沙箱内先完成依赖安装；依赖安装失败记为环境问题，不计入模型效果评估。随后借助 mini-swe-agent 内置 SWE-ReX 隔离 Docker 沙箱部署 harness 脚本，送入 LLM 生成的 payload 执行，捕获 stdout/stderr 完整运行日志。

数据记录：输出 run_logs/ 目录，逐条保存执行日志、退出码与执行耗时；沙箱启动失败、超时等异常完整记录。

### 步骤 S9：漏洞判定

两种判定模式待 E2 实验比选：

**模式 A：硬编码检测器。** 参考 DeepAudit 将检测器嵌入 harness 内部，由 mock 捕获 sink 函数入参并输出结构化检测结果。优点：确定性强，无 LLM 幻觉；局限：更适配注入类漏洞场景。

**模式 B：LLM 日志推理判定。** 判定规则由我方设计，DeepSeek 仅负责推理执行：

1. 输入证据集合：提取的源码、mock 定义、payload、harness 运行日志、报错信息、原始 SAST 告警、CWE 类型；
2. 使用固定提示词模板，要求区分两类失败原因：①mock／harness 环境错误；②payload 未能触发（**注意：payload 未能触发不等同于漏洞不存在**，可能只是构造不当，须结合重试与人工抽样复核判定）；
3. 强制输出结构化 JSON 结果：

```json
{
  "verdict": "TP|FP|Unconfirmed",
  "reason": "推理理由",
  "fix_suggestion": "改 mock | 改 payload"
}
```

数据记录：输出 verdicts.jsonl，记录告警编号、判定模式、verdict、reason、fix_suggestion、判定耗时与 token 消耗。

### 步骤 S10：重试闭环

外层编排程序维护重试计数器并设置最大重试上限（默认 3 次，可配置），读取判定模块返回 JSON 执行分支逻辑：

1. verdict=TP：确认为漏洞，保存 finding（harness、payload、运行日志），结束该告警验证；
2. verdict=FP 且 fix_suggestion 为 mock 错误：调用 DeepSeek 修改 mock 代码，重新组装 harness，再次送入沙箱执行；
3. verdict=FP 且 fix_suggestion 为 payload 未能触发：仅更新 payload，复用现有 harness，沙箱重跑；
4. 达到最大重试次数仍未得出确定结论：标记为「未确认（Unconfirmed）」，结束验证，**不计入误报统计**，单独统计其占比。

优化点：payload 未能触发场景无需重新生成 mock，减少 LLM 调用开销。重试与分支判决全部由外层确定性代码控制，LLM 仅输出结构化建议，保证实验指标稳定。

数据记录：输出 retry_trace.jsonl，逐次记录重试轮次、分支类型、修改内容与结果；统计各告警的重试次数分布。

## 3.7 报告汇总输出

### 步骤 S11：全链路结果汇总

外层编排程序汇总单条告警全链路处理结果：

1. 收集 LLM 静态理解输出、动态验证 verdict、harness 与 payload 证据、运行日志；
2. 结果去重，按照 CWE 类型、风险严重程度分级；
3. 区分结果类别：**已确认漏洞**（动态验证通过，附可复现 harness 证据）、**已排除告警**（确认为误报）、**未确认告警**（环境问题或达到重试上限，无法判定）；
4. 输出 JSON/Markdown 格式审计报告，包含项目统计摘要与每条 finding 详细信息。

数据记录：输出 audit_report.json 与 audit_report.md。

## 3.8 实验设计与对照

为量化本系统相对于基线的实际增益与代价，设计以下六组实验：

| 编号 | 实验名称 | 自变量 | 控制变量 | 观测指标 |
|---|---|---|---|---|
| E1 | 三方对照 | 工具配置（纯 Semgrep／纯 LLM（含静态理解、无动态验证）／本系统） | 数据集、提示词、模型 | 精确率、召回率、F1、误报率、动态验证确认率、未确认占比 |
| E2 | 消融实验 | 验证配置（无动态验证／仅模式 A／仅模式 B／完整重试闭环） | 数据集、模型 | 各组成部分的边际贡献；判定模式比选 |
| E3 | 跨基准泛化 | 评测基准（SARD 的 Python 子集：合成标注／Vul4Py：真实漏洞；若时间允许再补 Defects4J、Big-Vul 作跨语言扩展） | 模型、验证配置 | 结论在合成标注与真实漏洞基准上是否一致 |
| E4 | 跨模型泛化 | 大模型（2 个） | 数据集、验证配置 | 结论是否与特定模型绑定 |
| E5 | 成本与收益 | 验证配置 | 数据集、模型 | token 消耗、LLM 调用次数、沙箱执行次数、时延与可信度的权衡 |
| E6 | 典型案例溯源 | — | — | 成功与失败样本的逐条过程分析 |

其中 E1 用于确立基线，E2 用于支撑核心论点并完成判定模式比选，E3 与 E4 用于检验结论的普适性，E5 用于回答工程可行性，E6 用于技术展示与归因分析。

## 3.9 数据记录规范

实验数据统一存放于 records 目录，结构如下：

（1）env.json：环境与组件版本清单；

（2）dataset_manifest.json：数据集与抽样清单；

（3）sast_alerts.json：SAST 原始告警；

（4）alert_context.jsonl：告警去重与函数定位结果；

（5）static_findings.jsonl：LLM 静态理解结构化输出；

（6）extracted_snippets/：Extract 提取的源码片段；

（7）harness/：逐告警的 harness 脚本、mock 补丁与 payload；

（8）run_logs/：沙箱执行日志（含 env_snapshot.json 环境快照：镜像与 digest、依赖清单、依赖安装状态）；

（9）verdicts.jsonl：逐条判定结果；

（10）retry_trace.jsonl：重试过程记录；

（11）audit_report.json / audit_report.md：审计报告；

（12）metrics/：聚合指标与图表。

记录遵循以下原则：

（1）原始记录只追加不修改，任何修正均以新增记录的形式体现，避免事后篡改；

（2）每条记录携带完整元数据，包括运行编号、时间戳、模型标识、配置哈希与随机种子，以保证任一结论均可定位到具体的一次运行；

（3）派生数据（指标、图表）一律由脚本从原始记录自动生成，不手工填写；

（4）失败与异常样例同样完整记录，不予删除。

## 3.10 数据处理与指标计算

数据流向为：原始告警 → 静态理解输出 → 动态验证判定 → 采纳集 → 聚合指标 → 图表。

各指标的定义与计算方式如下：

| 指标 | 定义 | 计算方式 |
|---|---|---|
| 精确率、召回率、F1 | 采纳集相对于数据集真值的准确程度与覆盖程度 | 与数据集标注及人工抽样复核结果对比 |
| 误报率 | 采纳集中实际为误报的结论占比 | 人工抽样标注 |
| 动态验证确认率 | 已确认（TP）告警占进入动态验证告警的比例 | 由 verdicts.jsonl 统计 |
| **未确认占比** | 未确认（Unconfirmed）告警占全部候选告警的比例 | 由 verdicts.jsonl 统计；单独报告，**不并入误报** |
| 抑制正确率 | 已排除（FP）告警中经人工抽样标注确认为误报的比例 | 人工抽样标注 |
| **第三方复现率** | 抽样已确认漏洞中，由未参与该条验证的成员依据报告所附可复现材料独立复现成功的比例 | 交叉验证实测 |
| 人工复核成本 | 每条结论的平均人工复核耗时 | 抽样实测计时 |
| 开销 | token 消耗、LLM 调用次数、沙箱执行次数与端到端时延 | 由各记录的开销字段统计 |

人工标注方法：对采纳集与已排除告警分别按固定比例随机抽样，由两名成员独立判定该结论是否为真实漏洞，出现分歧的样本提交第三人仲裁，并记录标注一致性，以保证"精确率""误报率"与"抑制正确率"三项指标的客观性。

**第三方复现率**采用交叉验证方式测定：由未参与该条漏洞验证的成员，仅依据报告中附带的可复现材料（harness 脚本、payload、依赖与镜像版本、运行命令、运行日志）独立操作一遍，记录是否得到同一结论。该指标直接检验"可验证"是否成立，是本项目核心卖点的定量支撑。

结果呈现方式：

（1）E1 三方对照结果主表；

（2）"可信度—召回率"权衡曲线：量化"动态验证提升精确率"与"单元 harness 复现局限导致召回损失"之间的定量关系；

（3）E2 消融实验结果柱状图：量化无动态验证／仅模式 A／仅模式 B／完整重试闭环各配置的边际贡献；

（4）失败样例归因分析表：按"harness 无法组装／沙箱执行失败／payload 未能触发但经复核确为误报／跨文件依赖导致复现失败"等类别归因。

## 3.11 质量控制与可复现性

（1）版本固定：所有开源组件与 mini-swe-agent 固定到具体版本或 commit，记录于 env.json，全程不使用浮动版本。

（2）参数固定：大模型温度、提示词模板与随机种子在全部实验中保持一致，并完整记录。

（3）结果缓存：相同输入与配置的运行结果落盘复用，避免重复调用导致的结果漂移与调用配额浪费。

（4）失败如实记录：SAST 扫描失败、harness 无法组装、沙箱执行失败与复现失败的样本均完整保留，并在报告中作为方法局限（如 Extract-Mock-Test 丢失跨文件全局状态与净化逻辑）加以讨论，不做选择性呈现。

（5）数据真实性：全部指标、图表与截图均来自系统的实际运行输出，不篡改、不伪造、不夸大实验结果。
