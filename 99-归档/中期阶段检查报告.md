## 一、项目任务的主要内容和目标（对应评分 60 分）

### 1.1 项目任务的主要内容

本项目要解决的是代码审计中"**告警可信度**"问题，而非"检出率"问题。

静态应用安全测试（SAST）工具虽能批量产出告警，但误报率高，开发者必须逐条人工复核，最终往往因告警疲劳而弃用。大模型具备 SAST 所缺的跨函数与业务逻辑理解能力，因此业界普遍尝试"用大模型过滤 SAST 误报"。但这一方案把最终判断权交给了一个本身会产生幻觉的模型，形成"**用不可信去校正不可信**"的困境：

> 大模型说"这 400 条是误报，删掉吧"——开发者凭什么相信？模型判断错了，真漏洞就被**静默**丢掉了，过程中不会有任何报错。

本项目提出的任务是：**把判定依据从"模型的判断"换成"代码的执行结果"**，即对每一条 SAST 候选告警，在隔离沙箱中构造并实际运行该告警对应的代码，以**可复现的运行证据**判定漏洞真伪。

具体建设内容包括七个子模块：

| 编号 | 模块 | 内容 |
|---|---|---|
| C1 | SAST 扫描与告警预处理 | Semgrep 规则扫描；tree-sitter 定位告警所属函数节点；告警去重 |
| C2 | LLM 静态理解 | 以告警、局部源码与 CWE 为输入，输出结构化漏洞信息（source／transformations／sink／CWE） |
| C3 | Extract 代码提取 | 基于 tree-sitter 提取 sink 函数及同文件辅助函数，封装为独立可执行程序 |
| C4 | Mock 生成与 harness 组装 | 大模型生成 mock 桩与触发 payload，拼装为可独立运行的单元测试脚本 |
| C5 | 沙箱执行与判定 | SWE-ReX 隔离 Docker 沙箱执行 harness；硬编码检测器或日志推理判定 |
| C6 | 确定性编排与重试闭环 | 外层程序控制全部流程、重试计数与分支判决，LLM 仅出建议 |
| C7 | 报告汇总与评测 | 三分类结果、8 项指标、E1–E6 实验、可视化审计报告 |

### 1.2 项目目标与可量化的验收指标

本项目设定了三个可量化的工程目标，均给出明确的验收判据：

| 目标 | 验收指标 | 判据来源 |
|---|---|---|
| **动态复现能把误报压到什么程度** | 精确率、召回率、F1、误报率；相对纯 SAST 与纯 LLM 两个基线的提升幅度 | E1 三方对照 |
| **代价是否可接受** | 每条告警的 token 消耗、LLM 调用次数、沙箱执行次数、人工复核耗时 | E5 成本收益实验 |
| **结论是否真的可验证** | **第三方复现率**：抽样已确认漏洞中，由未参与该条验证的成员独立复现成功的比例 | 交叉验证实测 |

此外，项目对"**可验证**"给出了明确定义：

> 每条被采纳的漏洞结论均附带**第三方可独立重复**的验证材料——包括可执行的 harness 脚本、触发 payload、运行环境说明与完整日志，任何人据此可在自己的环境中复现同一结论。

该定义不同于形式化验证，也不同于可验证计算，是本项目区别于一般"LLM 辅助审计"方案的核心。

### 1.3 选题调研情况

**（1）选题来源**

选题直接对应企业真实需求："基于大模型对网络告警进行研判""利用 AI 大模型进行告警降噪"是当前安全产业的明确需求方向。本项目把"告警研判"聚焦到代码审计场景，并进一步聚焦到"如何可信地判定单条告警"这一具体环节。

**（2）同类工作对比**

调研了四类相关工作，并明确了本项目的差异位置：

| 工作类别 | 代表 | 与本项目的差异 |
|---|---|---|
| 传统 SAST | Semgrep、CodeQL | 它们是**本项目的输入源与基线**，不是被替代对象 |
| LLM 漏洞检测 | IRIS、RepoAudit 等神经符号方案 | 此类工作输出的是**判断**（这段代码有没有漏洞），本项目输出的是**证据**（这段代码被执行并触发漏洞） |
| LLM 误报过滤 | 用 LLM 对 SAST 告警做二次分诊 | 判定仍是自然语言推理，**结论不可独立复核**；这正是本项目要解决的问题 |
| 动态验证／自动复现 | DARPA AIxCC 系列 Cyber Reasoning Systems | 此类系统从零开始 fuzzing 以**发现**漏洞；本项目是**给定告警的定向复现**，规模小得多但更贴近工程现场的告警分诊场景 |

**（3）调研结论——识别出三个研究空白**

1. **误报过滤止步于"判断"，缺少"证据"**：现有方案未把"可验证性"作为系统设计的第一约束；
2. **动态验证类工作面向"发现"而非"定向复现给定告警"**：把 fuzzing 能力用于复现既有告警，尚未被系统化；
3. **缺少对"无法判定"这一类的诚实统计**：现有方案把"验证失败"默认算作误报，掩盖了方法局限。

本项目正是针对这三点展开。

### 1.4 选题的实践工作量说明

本项目的工作量体现在三个方面，均可交付、可检验：

**（1）三个技术栈的组合而非单一技术**

项目同时涉及**程序分析**（tree-sitter AST 切片、CWE 语义）、**大模型代码生成**（mock 桩与 payload）、**容器沙箱调度**（Docker 隔离执行）三条技术线，任一条未打通都会导致流水线不可用。

**（2）核心环节存在真实难点**

Mock 桩生成是全系统失败率最高的环节：大模型生成的 mock 常出现语法错误、依赖缺失、拦截逻辑不正确等问题。这要求项目组设计模板化生成策略、few-shot 示例与失败率统计机制，而非简单调用 API。

**（3）完整的实验设计与评测体系**

项目需要完成三方对照（纯 Semgrep／纯 LLM／本系统）与六组实验（E1–E6），并在公开数据集上产出八项指标的实测数据与图表，包括"可信度—召回率"权衡曲线。

**（4）工作量与周期的匹配性**

项目周期约 7 周（中期后至 12 月 4 日验收），四人分工后可并行推进三条技术线。项目已设置明确的分级降级预案（详见 2.4），确保在核心链路完成的前提下可按期交付。

## 二、项目的方案及分工（对应评分 30 分）

### 2.1 总体技术方案

系统采用"**静态候选 + 语义理解 + 动态复现验证**"的三段式路线，全部业务流程由确定性外层编排程序控制：

```
SAST 扫描（Semgrep）
   ↓ 原始告警
告警预处理（tree-sitter 定位函数节点、去重）
   ↓ 候选告警
LLM 静态理解（DeepSeek API）→ 结构化 source / sink / CWE
   ↓ 候选漏洞
动态验证（Extract-Mock-Test）
   ① Extract：tree-sitter 提取 sink 函数 + 同文件辅助函数
   ② Mock：LLM 生成 mock 桩 + 触发 payload，组装 harness
   ③ Test：SWE-ReX Docker 沙箱执行，捕获完整日志
   ④ 判定：硬编码检测器 / 日志推理 → TP / FP / 未确认
   ↓
确定性外层编排（重试计数、分支判决、预算控制、全程落盘）
   ↓
报告汇总与评测（三分类结果、8 项指标、E1–E6、可视化）
```

**三条核心设计原则**：

1. **判定依据必须是执行结果，不是模型表述**——保证结论可独立复核；
2. **流程控制权必须在确定性代码手里，不在 LLM 手里**——保证实验可审计、可回放，指标稳定；
3. **无法判定的必须单列，不能并入误报**——保证方法局限被如实呈现。

### 2.2 核心方案：Extract-Mock-Test 动态验证

这是本项目的技术核心，也是与同类方案的主要差异点。

**第一步 Extract**：用 tree-sitter 解析目标文件，提取 sink 函数及同文件内被直接调用的辅助函数，封装为独立可执行脚本。

**第二步 Mock**：调用大模型，传入提取的源码、sink/source 信息与 CWE 类型，生成 mock 补丁与触发 payload，把业务源码与 mock 桩拼装为可独立运行的单元测试脚本。mock 的作用是**拦截危险 sink 调用、捕获函数入参、返回模拟返回值**，从而在不产生真实副作用的前提下验证污点是否到达危险位置。

**第三步 Test**：先为被测项目准备依赖环境（依赖清单或预构建镜像），再借助 mini-swe-agent 的 SWE-ReX 隔离 Docker 沙箱部署 harness，送入 payload 执行，捕获 stdout/stderr 完整日志。

**第四步判定**：采用两种模式并由实验比选——模式 A 为嵌入 harness 的硬编码检测器（确定性强、无幻觉，适配注入类漏洞）；模式 B 为 LLM 日志推理（覆盖面宽）。模式 B 要求区分"mock／harness 环境错误"与"payload 未能触发"两类失败原因，且明确后者**不等同于漏洞不存在**。

**结果三分类（本方案的关键设计）**：

| 类别 | 判定 | 处理 |
|---|---|---|
| **已确认（TP）** | harness 跑通，payload 到达 sink 并构成漏洞 | 采纳，附可复现证据 |
| **已排除（FP）** | 日志表明不构成漏洞，或人工抽样确认为误报 | 否决，计入误报统计 |
| **未确认（Unconfirmed）** | 环境问题无法验证，或达到重试上限仍无确定结论 | 否决，**不计入误报统计**，占比单独报告 |

## 三、项目任务的背景和意义（对应评分 10 分）

### 3.1 项目背景的调研情况

**（1）行业痛点调研**

静态应用安全测试长期存在误报率偏高的问题。开发者需人工逐条复核，导致两种后果：一是**告警疲劳**，真实漏洞被淹没在噪声中；二是**信任流失**，开发者逐渐不再查看工具输出，安全左移难以落地。这一问题的本质不是检出力不足，而是**结论可信度不足**。

**（2）技术演进调研**

代码审计技术经历了四代演进：规则／模式匹配 → 数据流与污点分析 → 图分析（代码属性图）→ 神经符号（大模型 + 程序分析）。第四代虽提升了语义理解能力，但**报告可信度问题并未被作为一等问题处理**，这构成本项目的切入点。

**（3）国家与社会需求调研**

软件供应链安全已上升到国家层面。Log4Shell 等事件后，《网络安全审查办法》、SBOM（软件物料清单）相关标准相继落地，对"能否说清软件里有什么风险"提出合规要求。同时，课程教学计划明确要求介绍"软件安全开发基础"与"编程规范，提升代码安全性"，并将"规范编程能力"纳入职业素养考核——**本选题与课程大纲高度一致**。

### 3.2 法律法规因素的考虑

本项目在方案设计与实施过程中，系统考虑了以下法律法规因素：

| 法律法规／规范 | 本项目对应措施 |
|---|---|
| 《中华人民共和国网络安全法》 | 被审计对象**全部为公开数据集与开源项目**，不审计任何未授权的第三方系统，不实施任何未授权访问 |
| 《中华人民共和国数据安全法》 | 实验数据均为公开数据，不涉及真实业务数据与敏感数据 |
| 《中华人民共和国个人信息保护法》 | 不处理任何真实个人信息；如公开代码中含类个人信息示例，不予采集与存储 |
| 《生成式人工智能服务管理暂行办法》 | 遵守所用大模型 API 的服务条款与内容安全要求 |
| 《网络安全审查办法》 | 作为软件供应链安全的合规背景，在项目背景调研中予以论述 |

**针对"动态执行"这一特殊环节的额外合规设计**——这是本项目与其他方案的重要区别：

1. **所有执行在隔离 Docker 沙箱中进行**，与宿主机隔离；
2. **mock 桩拦截危险 sink 调用**（如数据库执行、系统命令、文件写入），使被测代码**不产生真实副作用**；
3. **payload 为合成构造的测试输入**，不含真实攻击载荷；
4. **不针对任何真实系统**；产出的 harness 与 payload 仅用于验证告警真伪，不得用于攻击活动；
5. 项目中将在显著位置标注"**仅供安全研究与教学使用**"。

此外，项目重视开源许可证合规。技术底座涉及 Semgrep（LGPL-2.1，通过 `pip install` 且不修改源码、纯进程调用，不触发开源义务）、tree-sitter（MIT）等组件，交付物中将附**第三方组件清单**（名称、版本／commit、许可证、使用方式），并在报告中明确"**不将他人的代码作为本组工程实践成果提交**"。

### 3.3 项目意义

1. **现实意义**：让自动化代码审计的结论真正可被工程采用——开发者不只能看到"这是漏洞"，还能亲手跑一遍看到它被触发，从而愿意信任并使用工具输出。
2. **方法意义**：把"误报抑制"从**模型判断问题**转化为**程序可执行性与环境构建问题**，后者是工程上可解决、可度量的；同时以"未确认单列"的方式如实刻画方法局限，避免指标美化。
3. **课程意义**：项目覆盖调研、方案设计、系统实现、实验测试、文档撰写与技术展示全流程，与教学计划的软件安全开发内容直接呼应，能够充分锻炼信息安全专业知识的综合运用能力。

## 五、存在的问题与下一步计划

### 5.1 当前存在的主要问题

| 问题 | 说明 | 应对 |
|---|---|---|
| Mock 生成成功率不稳 | 大模型生成的 mock 可能出现语法错误、依赖缺失、拦截逻辑不正确 | 采用模板化 + few-shot 生成；将组装失败率作为独立观测项；设重试上限 |
| 跨文件上下文缺失 | Extract 仅取同文件函数，会丢失跨文件 source 与净化逻辑 | 优先选用单文件样本（SARD 天然满足）；跨文件样本归入"未确认"并如实统计 |
| 被测项目依赖环境不确定 | harness 依赖第三方库，环境不全会导致执行失败 | 维护依赖清单或预构建镜像；安装失败记为环境问题，不计入模型效果 |
| 判定归因困难 | 执行失败时区分"环境错"与"payload 错"较难 | 以模式 A 硬编码检测器为主；模式 B 仅辅助；必要时人工抽样复核 |
